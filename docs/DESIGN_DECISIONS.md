# Design decisions - resolution of the eight open items (design doc, Section 22)

| # | Item | Decision (implemented in) |
|---|---|---|
| 1 | A 10-min window cannot observe a 15-min idle | Abandonment uses **per-customer stateful processing with a processing-time timeout** anchored at `last_event_ts + 15 min` (`c360/core/cart_state.py`, `stream_cart_abandonment.py`). `session_window` was rejected: it only closes when the *watermark* advances, which stalls when traffic stops -> alerts could be late. The 10-min/1-min sliding window is still computed (`cart_activity_windows`) as a live activity metric for BI. Alert latency is bounded by the trigger interval (5 s) -> well inside 60 s. |
| 2 | Exactly-once Kafka -> HBase | Claimed as **exactly-once effect**: checkpointed offsets+state, deterministic `alert_id` (sha1 of cart + last event), Delta `MERGE` on `alert_id`, HBase puts with the event time as cell timestamp (replays overwrite with identical data, older data never beats newer), notifier de-dups on `alert_id`. Kafka producers use idempotence + `acks=all`. |
| 3 | Olist vs Retailrocket ids | Deterministic hash mapping of `visitorid`/`itemid` onto master customer/product ids (`c360/core/identity.py`, `retailrocket_adapter.py`). Replays get stable `event_id`s so they de-duplicate. |
| 4 | Topics | `cart_events` (6 partitions, key=customer_id), `brand_mentions` (3), `weather_events` (1), `cart_alerts` (3). All RF=3, `min.insync.replicas=2`, unclean leader election off (`kafka/create_topics.sh`). |
| 5 | Sqoop retired | Sqoop script kept because the spec names it (saved job, `lastmodified`, `--merge-key`); **Spark JDBC incremental** (`jdbc_incremental.py`) is the maintained equivalent with a watermark committed only after a successful write. Debezium/CDC is the next step if sub-minute batch freshness is needed. Airflow tries Sqoop first and falls back to JDBC. |
| 6 | KPI formulas | `kpi/measure_kpis.py` docstring. **Recovery rate** = alerted carts followed by a purchase within 7 days / alerted carts; the **target must be judged as lift vs a 10% no-message holdout**. In the synthetic data the *natural* rate without any intervention is already ~20%, so a raw "18%" would be meaningless. **LTV uplift** = mean 90-day forward revenue, treated vs baseline cohort. |
| 7 | On-prem vs cloud | HDFS+Hive+HBase = operational/serving; S3+Glue+Athena+Delta = analytical. Gold Delta is the system of record; `aws/s3_sync.py` mirrors gold to S3 nightly (Airflow task `s3_sync`); HBase is a *derived* serving cache rebuilt from gold (`hbase_sync.py`) plus real-time `c:` cart cells. Lake roots are env-configurable (`file://`, `hdfs://`, `s3a://`, `dbfs:/`) so the same jobs run in both places. |
| 8 | Vector store / embeddings | `sentence-transformers/all-MiniLM-L6-v2` (384-d, CPU) + exact cosine search over a NumPy matrix, with metadata filters (customer, type). Exact search is right below ~1M chunks; the `VectorStore` interface lets you swap in FAISS/Chroma/OpenSearch. LLM answers via the Anthropic API with a grounding prompt that forces citations and an "I can't find that" refusal. TF-IDF fallback embedder for offline/test use. |

## Other choices worth knowing
* **State-machine in plain Python**, wrapped by `applyInPandasWithState`: unit-testable, and reused as the independent oracle in reconciliation.
* **De-dup inside the state** (bounded list of recent event ids) rather than chaining `dropDuplicates` before a stateful operator; global de-dup happens in Silver via `MERGE ... WHEN NOT MATCHED`.
* **Replay at 100x**: events are re-stamped to "now" and carry `speed`; the detector divides the idle threshold by `speed` (15 min -> 9 s) so replay exercises the same code path.
* **HBase column families by owner**: `p`,`m` batch-owned; `c` stream-owned -> the nightly sync can never clobber live cart state.
* **ML**: point-in-time features, temporal train/val/test split, threshold for F1 tuned on validation only.
* **Power BI**: a `.pbix` cannot be generated by code; `bi/` has the spec, DAX and extracts. The 1-minute refresh requirement depends on Power BI licensing - see `bi/DASHBOARD_SPEC.md`.
